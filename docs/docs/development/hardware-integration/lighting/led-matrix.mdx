## Configure and test a Corne54

Each half has a chain of 28 WS2812 LEDs. First build the stock configuration. Then change one color or key binding so you can verify the result on the keyboard. The files below are in the [Corne54 board directory](https://github.com/afayge/zmk/tree/main/app/boards/bmk/corne54).

### 1. Enable lighting and choose a startup state

Both `corne54_left_defconfig` and `corne54_right_defconfig` include these settings. When porting the configuration, put them in the corresponding board or user `.conf` file. Saved lighting settings take precedence over startup defaults.

```ini
CONFIG_ZMK_LED_MATRIX=y
CONFIG_ZMK_LED_MATRIX_ON_START=n
CONFIG_ZMK_LED_MATRIX_BRT_START=40
CONFIG_ZMK_LED_MATRIX_AUTO_OFF_IDLE=y
```

Corne54 also enables `CONFIG_ZMK_EXT_POWER` and `CONFIG_ZMK_LED_MATRIX_EXT_POWER` to switch strip power through a board GPIO. On another keyboard, check the schematic for a controllable LED supply before enabling those options.

### 2. Map switch positions to local LED numbers

`corne54.dtsi` defines `led_strip`, a chain length of 28, and GRB color order. This excerpt from `corne54_left.dts` shows the entire left-hand grid and one solid-color preset. Edit the existing node when working on a Corne54. The two includes provide the grid tokens and color constants.

```dts
#include <dt-bindings/zmk/led_matrix.h>
#include <dt-bindings/zmk/led_matrix_colors.h>

/ {
    chosen {
        zmk,led-matrix = &led_matrix;
    };

    led_matrix: led_matrix {
        compatible = "zmk,led-matrix";
        led-driver = "strip";
        led-strip-device = <&led_strip>;
        led-count = <28>;
        matrix-led-grid = <
            0 1 2 3 4 5 LM_BREAK
            6 7 8 9 10 11 LM_BREAK
            12 13 14 15 16 17 LM_BREAK
            18 19 20 21 22 23 LM_BREAK
            LM_PH LM_PH 24 25 26 27
        >;

        profile0 {
            profile-id = <0>;
            display-name = "Palette";
            renderer = "solid";
            colors = <LM_PALETTE>;
            brightness = <100>;
        };
    };
};
```

Fill in the grid in local switch-scan row and column order. On a direct strip the logical LED number is the zero-based position of the pixel in the chain. Use `LM_BREAK` between rows, `LM_PH` for a cell without a switch, and `LM_NOLED` for a switch without a light. The right half has its own grid in `corne54_right.dts`. Its last row is `27 24 25 26 LM_PH LM_PH`. If a key lights its neighbor, inspect that half’s grid. If red appears green across the strip, inspect the strip’s `color-mapping`.

| Hardware                              | Controller properties                                                   | Mapping                                                                                                                                                  |
| ------------------------------------- | ----------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Addressable RGB strip                 | Set `led-driver = "strip"` and point `led-strip-device` at the strip.   | Number pixels in chain order. The grid locates each pixel under a switch.                                                                                |
| One Zephyr LED device                 | Set `led-driver = "matrix"` and point `led-device` at the controller.   | Use `channel-indexes` to map R, G, and B when the device supports `write_channels`. For a per-LED API, use `led-indexes` to map physical LEDs.           |
| Multiple controllers or mixed devices | Select `"matrix"` and point `led-device` at a `zmk,led-composite` node. | Assign each child a contiguous `channel-offset` and `channel-count`, starting at zero. Map logical RGB channels into this space using `channel-indexes`. |

### 3. Bind lighting controls

`corne54.keymap` includes `<dt-bindings/zmk/led_matrix.h>` and places the controls on the Fn layer. To adapt another keymap, replace individual entries in an existing layer’s `bindings`. Use `&lm LM_TOG` for power, `&lm LM_EFF` for the next effect, `&lm LM_BRI` for brightness up, and `&lm LM_STA LM_STA_ALL` to show configured status indicators. Preset 0 uses `LM_PALETTE`, so `&lm LM_HUI` changes its color. For fixed red, set the preset’s `colors` to `<LM_RED>`.

### 4. Build and verify both halves

From the repository root in an initialized west workspace, run:

```sh
west build -s app -b corne54_left -d build/corne54_left
west build -s app -b corne54_right -d build/corne54_right
```

Flash the `zephyr/zmk.uf2` from each build directory to its matching half. With the factory defaults the lights start off. Toggle them on from the Fn layer, select a different preset, and change the brightness. Select a reactive preset and test each row on both halves. Use the status key to verify the battery, Bluetooth, or lock indicators configured on that half.

See the [technical reference](../../../led-matrix-led-composite-reference.mdx) for layer colors, overlay priority, independent zones, Studio editing, and power timing.

## Overview

`LED Matrix` is an RGB controller that sits above the hardware backend. It is not tied to a single LED family; instead, it renders multiple sources into one logical LED space: base profiles, layer colors, independent LED containers, and Battery/USB/BLE/HID status overlays.

- `RGB underglow` targets addressable strips and talks directly to `led_strip` drivers.
- `Backlight` targets single-color parallel LEDs and mainly controls brightness.
- `LED Matrix` targets a logical RGB matrix and can use either a Zephyr `led` backend or a direct `led_strip` backend.

`led-driver = "matrix"` means LED Matrix writes through the Zephyr `led` API. The target can be a matrix driver chip or an aggregator such as `led_composite`. `led-driver = "strip"` means LED Matrix writes directly to the Zephyr `led_strip` API.

`led_composite` is not a renderer. It is a backend adapter that exposes a single flattened RGB channel space built from multiple `led-device` and `led-strip-device` children, which `zmk,led-matrix` can then map with `channel-indexes`.

### Backend selection notes

- `CONFIG_ZMK_LED_MATRIX_USES_LED_API` and `CONFIG_ZMK_LED_MATRIX_USES_LED_STRIP_API` are hidden helper options derived from the chosen `zmk,led-matrix` node.

- With `led-driver = "strip"`, `CONFIG_ZMK_LED_MATRIX` selects `LED_STRIP`.

| Macro                              | Meaning                                            |
| ---------------------------------- | -------------------------------------------------- |

## DTS Structure

### Top-level `zmk,led-matrix` properties

| Property                                                                                                            | Required               | Meaning                                                                                         |
| ------------------------------------------------------------------------------------------------------------------- | ---------------------- | ----------------------------------------------------------------------------------------------- |
| `led-driver`                                                                                                        | Yes                    | `"matrix"` or `"strip"`; selects backend API                                                    |
| `led-device`                                                                                                        | Conditionally required | Required when `led-driver = "matrix"`                                                           |
| `led-strip-device`                                                                                                  | Conditionally required | Required when `led-driver = "strip"`                                                            |
| `led-count`                                                                                                         | Yes                    | Number of logical LEDs                                                                          |
| `output-channel-count`                                                                                              | No                     | Total physical output channels; defaults to `led-count * 3`                                     |
| `channel-indexes`                                                                                                   | No                     | Logical RGB to physical channel map for write-channels backends; length must be `led-count * 3` |
| `led-indexes`                                                                                                       | No                     | Logical LED to physical LED mapping for non-write-channels backends                             |
| `matrix-led-grid`                                                                                                   | No                     | Local RC grid for position-driven renderers and layer colors without explicit `layer-leds`      |
| `battery-leds`, `ble-profile-leds`, `usb-leds`, `hid-*-leds`                                                        | No                     | Logical LEDs used by status overlays                                                            |
| `battery-color-*`, `ble-color-*`, `usb-color-*`, `hid-*-color-*`                                                    | No                     | Colors for each status source                                                                   |
| `status-timeout-ms`, `usb-timeout-ms`, `ble-timeout-ms`, `hid-timeout-ms`, `battery-timeout-ms`, `ble-pairing-hold` | No                     | Automatic status duration and BLE open hold policy                                              |

### Child node models

| Child kind                | Key property        | Common properties                                                             |
| ------------------------- | ------------------- | ----------------------------------------------------------------------------- |
| display profile           | `profile-id`        | `display-name`, `renderer`, `colors`, `brightness`, `period-ms`, `keypress-*` |
| layer color entry         | `layer-id`          | `layer-colors`, `layer-leds`, `brightness`, `display-time-ms`                 |
| independent container     | `independent-id`    | `independent-leds` plus nested local profiles                                 |
| independent local profile | nested `profile-id` | `renderer`, `colors`, `brightness`, `period-ms`                               |

Child node constraints:

- When `layer-leds` is omitted, the target LEDs default to the traversal order of `matrix-led-grid`.
- `independent-leds` must be unique and must not overlap other independent containers.
- When `matrix-led-grid` is present, `independent-leds` must not also appear in that grid.

## `led_composite`

### Core concept

`zmk,led-composite` uses child nodes to flatten multiple backends into one continuous RGB channel space. Each child declares its offset and length inside that flattened space.

| Property           | Required   | Meaning                                                                     |
| ------------------ | ---------- | --------------------------------------------------------------------------- |
| `led-device`       | one of two | Child backend that exposes the Zephyr `led` API                             |
| `led-strip-device` | one of two | Child backend that exposes the Zephyr `led_strip` API                       |
| `channel-offset`   | Yes        | Start offset in the flattened channel space                                 |
| `channel-count`    | Yes        | Writable RGB channels; strip and scalar children use three channels per LED |
| `ext-power-device` | No         | Optional shared power controller for strip children                         |

The constraints are:

- Each child must define exactly one of `led-device` or `led-strip-device`.
- Child ranges must start at `0`, be declared in ascending order, and remain contiguous with no overlaps or holes.
- When multiple strip children use `ext-power-device`, they must share the same device.
- An `led-device` prefers `write_channels`, then `set_brightness`, and finally paired `on` / `off` callbacks.
- A brightness/binary scalar child needs three channels per physical LED; the maximum RGB component becomes its scalar brightness.

### public API and capability macros

`app/include/drivers/led/led_composite.h` exposes the following interface:

- `ZMK_LED_COMPOSITE_CAP_MANAGED_POWER`: Child backend supports managed power.
- `ZMK_LED_COMPOSITE_CAP_FULL_HARD_OFF`: Child backend supports full hard-off.
- `zmk_led_composite_get_channel_count(const struct device *dev, uint32_t *count)`: Query total channel count.
- `zmk_led_composite_get_capabilities(const struct device *dev, uint32_t *caps)`: Query capability bitmap.
- `zmk_led_composite_power(const struct device *dev, bool enable)`: Enable or disable composite power state.

            display-name = "Composite Mixed Power";
            renderer = "solid";

### 7. BlackBerry Trackball PWM LEDs

The four WHT, GRN, RED, and BLU outputs can use standard `pwm-leds`. A 1 ms period with
`PWM_POLARITY_NORMAL` is active high; the board DTS supplies the actual controllers, channels, and
pinctrl configuration.

```dts
#include <zephyr/dt-bindings/pwm/pwm.h>

/ {
    trackball_leds: pwm_leds {
        compatible = "pwm-leds";
        wht { pwms = <&pwm0 0 PWM_MSEC(1) PWM_POLARITY_NORMAL>; };
        grn { pwms = <&pwm0 1 PWM_MSEC(1) PWM_POLARITY_NORMAL>; };
        red { pwms = <&pwm1 0 PWM_MSEC(1) PWM_POLARITY_NORMAL>; };
        blu { pwms = <&pwm1 1 PWM_MSEC(1) PWM_POLARITY_NORMAL>; };
    };
};
```

If no other LEDs exist, use `&trackball_leds` directly as the LED Matrix `led-device` with
`led-indexes = <0 1 2 3>`. With an existing channel backend, append the PWM device as a scalar
composite child:

```dts
trackball {
    led-device = <&trackball_leds>;
    channel-offset = <6>;  /* Example: the keyboard backend uses channels 0..5. */
    channel-count = <12>; /* 4 physical LEDs * 3 logical RGB channels */
};
```

Put the four logical LEDs in one independent container and define a local profile for every
combination and brightness. `&lm LM_CFS(0, 2)` atomically switches group 0 to profile 2. `LM_BRT`
remains global, and settings persists the independent profile selection.

## Troubleshooting

| Symptom or diagnostic                      | What to check                                                                                                                                                                                                                             |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Controller missing or backend unavailable  | Set `chosen { zmk,led-matrix = &led_matrix; };` at the root. Use `led-device` for a matrix backend and `led-strip-device` for a strip. Check that the target device is enabled.                                                           |
| Empty controller fails to initialize       | With the runtime editor disabled, provide a main preset, independent group, layer color, or status zone.                                                                                                                                  |
| LEDs show the wrong channels               | For a `write_channels` backend, provide exactly three entries per logical LED in `channel-indexes`. Each entry must fit in `output-channel-count`. For a driver using per-LED calls, use `led-indexes`.                                   |
| Position-driven effects fail to initialize | Provide a local `matrix-led-grid` matching the switch-scan dimensions. A layer color without a grid needs explicit `layer-leds`.                                                                                                          |
| Independent group fails to initialize      | Number independent groups and their local presets consecutively from zero. Check for duplicate LEDs, overlaps between groups, or a factory group that also lists grid LEDs.                                                               |
| Composite fails validation                 | Give each child exactly one backend. Arrange its channel range immediately after the preceding one, starting at zero. A strip needs an integral number of RGB triples. All strips specifying external power must use the same controller. |
| A scalar child has the wrong channel count | Reserve three channels per physical LED. A brightness device needs `set_brightness`; a binary device needs both `on` and `off`.                                                                                                           |
